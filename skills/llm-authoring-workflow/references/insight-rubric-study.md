# Insight 与核心考点写法：返修案例、对照研究与局限

研究日期：2026-10-20（北京时间）。这是原研究的通用公开版，保留研究方法、统计、案例变化及结论局限；案例名称与表述作归纳处理，不发布私人题面、模型原文、任务ID、哈希、Cookie或原始请求回执。本报告仅针对考点质检，不把题目难度检查、达成性检查或项目最终验收混为一谈。

## 结论与适用范围

有依据的改进方向已经找到：突出改变决策的机制、补齐真正遗漏的目标、使用可以从回复直接判断的考点、放开等价路径、移走非必要的附带要求。但本轮没有验证出能够“大概率通过当前 API”的固定写法。

原因是：连历史实际通过的原输入，本轮也未复现通过。因此，下面的写法应作为提高专业质量和判定清晰度的建议，不能包装为现行检查器的通关公式。Insight 仍可用自然段、机制推导、比较或结论加边界等不同形式，避免批量使用同一套句式。

## 研究了什么，实际得到什么

历史固定快照覆盖 v2/v3 的14道题、53次请求、33份不同 payload。这里的 payload 指实际发送的 JSON 载荷，哈希按项目 canonical JSON 算法计算，不等于文件字节哈希。历史有9次实际通过、14次不通过、6次无法质检、24次服务错误；找到3组题面及三份模型回复不变的失败→返修→实际 API 通过。重复检查、定向挑样及服务故障都存在，不能用9/53估计题目的合格率。依据：历史对照与原文（原始证据本地留存）、固定数据快照（原始证据本地留存）。

本轮完成 **34次独立研究调用**，涉及10道题：

| 返回类型 | 次数 | 应怎样理解 |
|---|---:|---|
| 明确通过 | 0 | 本轮未得到成功样本 |
| 明确不通过 | 26 | 逐项复核具体理由，不自动相信根因标签 |
| 无法质检 | 5 | 结论未知，不能算通过，也不能据此断言写法不合格 |
| HTTP 400 | 2 | 故意将 from_agentic 改为布尔值的协议探针，属参数拒绝；不能当作503或文案失败 |
| HTTP 200、业务码0，但内容为空 | 1 | 无有效质检结论 |

其中，8道题的8份历史实际通过载荷，共原样重放10次，均未复现通过。其余试验覆盖 Insight 压缩、突出机制到决策的连接、考点动作化、删除一条附加条件、补真正缺项、等价路线、可选边界归位、条目顺序和少量协议诊断。完整输入和反馈见逐次实验表（原始证据本地留存），统计见实验统计（原始证据本地留存）。这是定向对照研究，样本并不独立随机，0/34仅是本轮观察值，不能据此推算所有任务的通过概率。

案例B的返修稿在研究当天有实际API通过记录。随后两次原样复测均不通过，发送的JSON载荷与原通过输入一致。另有用户报告的网页通过，因来源和输入绑定证据不同，没有计入实际API通过次数。

## 更值得采用的写法

### 1. Insight 先回答“什么因素真正改变了选择”

Insight 应把关键机制与这道题的决策连起来：哪一种看似合理的直觉在题设条件下会失效，为什么失效，因而该选什么或排除什么。背景百科、注意事项和评分规则不能代替这段关系。

例如 案例B 的有效内容是：相对湿度更高不代表叶周失水驱动力更小；题设中的温度变化使比较方向反转，因此不能靠透明罩直晒追求更高的湿度读数，配置要同时处理热负荷与局部保湿。这里真正关键的是温湿联动怎样改变推荐，而非在开头贴“反直觉”“高阶”标签。

不用把所有边界挤进第一句话。先写决定性关系，再补需要的适用限制。也不要把一篇养护方案或评分细则全部搬进 Insight。该原则在历史成功稿中有实例，但本轮没有验证出固定篇幅或段数的通过优势。案例B 返修对照（原始证据本地留存）

### 2. 考点判断一个结论或关系，给出可见的最低证据

可以问：裁判能否仅靠目标回复指出这条达成或未达成，而不用替模型补推理、猜设备能力或要求某个术语？

弱表述示意：“充分考虑温湿度，推荐合理方案。”它没有说清需要判断的关系或结果。

更清楚的表述示意：“结合两组温湿读数，判断罩内的叶气水汽压差高于敞放环境；计算或等价文字比较均可。”这条在判断一个比较关系。它不是要求模型逐一复读一串关键词，也不强制精确小数或专用缩写。

一条可判定的因果关系可以保留前提与结论，不必机械拆成数条。真正应分开的，是能各自独立满足的要求，例如设备推荐、无人运行、光照处理，避免一项没写就让整包要求全部失分。

### 3. 补真正遗漏的核心目标，别让替代方案冒充目标已经实现

先检查“题面目标→Insight→核心考点”能否对应。若 Insight 明明说某种保守替代只能保安全、不能保证体验目标，考点却只考安全，就会把未完成用户目标的回答判为全达成。

案例A 是最清楚的例子：原考点检查了返程时间、路线和通道风险，却没判近岸观海替代是否仍能保证看潮池；返修补上目标取舍后历史实际通过。该变化确实增加了有用的判定覆盖，不能简单概括成“加一条就过”。因为 Insight 与其他点也同时修改了，尚不能认定新增一条独自造成通过。失败原回执（原始证据本地留存）、返修通过原回执（原始证据本地留存）

### 4. 把必需条件、可选增强、作者判定边界分开

“不做某项调整，不代表其他调整全被禁止”通常是理解边界，不一定要变成模型必须另外说出的一条要求。

案例C 的同题对照尤其有价值：prompt、Insight、三份回复均相同。简化对照：旧D3同时写有“不因凑心率比例额外加间歇”和“允许原质量课内部调整”；通过版D3只判“不为凑比例额外加课”，把内部调整保留为理解边界。这是归纳示例，不是原题或原考点的完整发布。D1、D2也作了动作化改写。它支持优先减少条目附带负担，不能证明只删后半句就必过：本轮确实做了只删该句的试验，仍不通过。原失败回执（原始证据本地留存）、原通过回执（原始证据本地留存）

可选增强只有在确有独立比较价值时才放非决定性点；普通解释性豁免留在作者判定说明即可。不需要为了容纳每一条质检建议把非决定性点无限加长。无非决定性点时填“无”。

### 5. 用机制和功能界定等价方案，避免品牌、术语或隐藏阈值

例如 案例B 的无人条件，重点是核心配置怎样覆盖离家时段，被动围护与自动供湿都可成为不同实现路径。不能只认“自动”二字，也不能把设备名自动当作它具备一切未写出的能力。最低证据应与题面实际需要相称。

每条考点尽量围绕核心，必要的接受边界紧随该点或留在判定说明；不另设隐性门槛。不是题面真正需要的品牌、固定小时、精确参数、特定名词，不能为了把 Seed 判未达成而临时补入。专业合理且同样完成任务的替代方案应按同一标准接受。

## 三组返修，究竟能学到多少

| 案例 | 有价值的改变 | 证据强度与限制 |
|---|---|---|
| 案例A 潮池路线 | 将安全替代与用户体验目标的差别纳入判定 | 历史修后实际通过；多字段变化，本轮旧通过稿未复现 |
| 案例B 铁线蕨返修 | 用更直白的因果表达，补具体配置的保湿机制与无人运行方式 | 历史修后实际通过；原失败理由存在本地异议，本轮原样复测未复现 |
| 案例C 跑步训练 | 保留 Insight，条目动作化，减少 D3 的附带要求 | 历史修后实际通过；随后扩写又失败，本轮删句、改关系及缩短均未成功 |

完整前后原文、哈希与原返回在历史研究（原始证据本地留存）。这些例子支持审慎改进，不能证明它们比未修改稿在现行检查器中有更高的统计通过率。

## 常见问题写法与应对

| 写法或现象 | 问题 | 建议 |
|---|---|---|
| 只列常识、背景和注意事项 | 看不出什么关系决定本题选择 | 保留关键前提、推理转折与选择后果 |
| “合理、充分、适当、兼顾”替代判断标准 | 达成边界不明确 | 写可观察的比较、推荐、解释或排除结论 |
| 一条里堆结论、设备、例外、参数、追踪方案 | 独立条件被捆绑，难以稳定判定 | 分开独立要求；仍属于同一因果关系的内容保留 |
| 把 Insight 每句话都升成决定性点 | 背景或配套细节变成硬门槛 | 用“缺了是否仍能正确完成核心任务”复核必要性 |
| 因反馈建议不断追加例外与最低要求 | 条目越来越长，新的歧义更多 | 先判断建议是否真的解决专业或判定缺陷 |
| 为维持 Seed 失分临时收紧解释 | 容易出现题外标准与选择性评分 | 统一标准复评所有原文，接受门槛真实失败 |
| 以字数短或术语多推断一定易过 | 历史长稿也通过；本轮短稿也失败或无法质检 | 不设未经验证的字数、句数或术语配额 |

这张表是质量建议，不是由本轮实验验证的失败原因排行榜。本轮26次明确失败中，有26次含“缺少合格的 Insight”标签，但不能因此认定这些输入都真的缺少洞察。

## 不能机械接受的反馈

1. 总结称“缺少 Insight”，详情却认可决定性机制并给90多分：保留外部原结论与本地异议，要求定位具体欠缺，不凭高分擅自标通过，也不凭总标签推翻全部内容。
2. 反馈引用的句子并不存在：条件报名例 的一份原返回指称 Insight 出现“人数不能等同于最终到场人数。；”，实际请求无该原句。先核对 request，再决定是否有真实文字问题。该返回（原始证据本地留存）
3. 一面要求单点聚焦，一面让同一点加更多豁免：将有用边界放到正确位置，不无限补丁。案例C 原样重放中，反馈还把 Insight 里的“允许原课内部调整”当成仅写“不额外加课”的 D3 自带要求；须逐字区分作者说明与条文本身。14次阶段性输入审计（原始证据本地留存）
4. 提出新的科学判断或设备效果：仍须以可靠资料和题设为准。例如不能仅因反馈列出托盘，就无条件断言它满足单盆持续供湿；也不能把心率响应滞后泛化为所有协议下总高心率时间都必然低估。这里记录的是应复核的边界，未把服务建议当科学事实。
5. “无法质检，未发现需要展示的问题”：没有可据以修复的明确内容理由，不把它改写成通过，也不编造一种写作病因。

## 对调用链的核验与尚不能确认的事

所有34次请求及回执的绑定、载荷、传输和 manifest 哈希均有效；所有变体的 prompt 与三份真实模型回复保持原内容。原历史53份请求仍与采样快照一致。原样重放的通过稿确实与原发送载荷相同，未把研究元数据塞进模型输入。采用现有生产 client、同一检查 plan/provider/平台 task 配置，只调用 invoke；未调用保存/正式提交或模型生成接口。最终完整性审计（原始证据本地留存）

协议探针中，增加正确领域/题型或移除 from_agentic 未改善结果；把原字符串 "true" 改为布尔值 true 返回 HTTP400。因此没有依据把生产字段改成布尔值。没有出现需要更新 Cookie 的返回，本轮未改 Cookie。

可以确认的是：相同 JSON 输入在不同时点产生了不同结论。不能确认的是：到底属于评测器随机性、规则/模型升级、账号上下文、解析/聚合或其他后端变化。历史没有完整请求头和服务端版本，不能宣称整个 HTTP 会话完全相同或已确定后台 bug。

## 推荐的写作与返修做法

先按[简明检查单](insight-rubric-checklist.md)做一次专业自查，修正真正的目标遗漏、因果断层、隐性条件和复合要求。收到明确失败后，将理由分为认可、不认可、无法定位；认可的修复到具体点，不认可的保留输入绑定与原文证据，无法质检或空结果单独记录。

正式采用任何研究变体时，另建版本，统一重评全部既有模型。Seed 未全部达成、GPT/Claude 至少一个全部达成的门槛仍须真实成立；基质处理例 的后续复核已纠正为三家全达成，不能靠润色复活题目资格。prompt 改变时重新采集，不能把旧回答绑给新题。

通过但附有建议时，只处理值得采纳的表达优化，不把每条建议增加为决定性门槛；若只是表达整理，按既有流程无需为了建议再刷检查。若实际改变标准或题面，则不能把旧回执说成新输入的独立通过。

本轮已达到研究方案中的“跨题历史正控无法复现、继续细改难以归因”的停止条件。没有继续以拿到一次通过为目的循环。本次将其中有专业依据的质量建议作为工作流必读参考，不把它们登记为已验证提高API通过率的规律。正式冻结稿、回复、判断、交付和历史回执保留；公开报告不包含私人题库或原请求。

## 可直接给项目方的复现说明

> 多份历史通过输入在当前原样复测时均未复现通过，请协助确认现行Insight合格标准、模板或模型是否变更，以及“无法质检、未发现需要展示的问题”的准确含义。我们保留了相同输入的前后请求与返回，可在获准后提供不含认证或会话信息的具体对照；该现象尚不能确认具体后端原因。
