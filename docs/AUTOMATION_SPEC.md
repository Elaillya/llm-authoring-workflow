## 当前浏览器执行路径（2026-10-26）

自动化分支默认采用 ego-lite。启动、pi-web 衔接及截图见[浏览器手册](../skills/llm-authoring-workflow/references/automation-playbook.md)；平台填写、修改、暂存、质检、上传、恢复和交接的执行步骤统一见[平台操作流程](../skills/llm-authoring-workflow/references/platform-automation.md)。本节覆盖下文历史轮次中“旧平台配方优先”的执行方式，其余业务合同保持。

- 批量文本与状态读取使用通用 `ego-platform.mjs`；下拉、按钮、文件上传使用 ego 标准接口，定位优先 `data-field-id`。不新增工作流状态机或平台强制门禁，不复刻平台 HTTP。
- 底层 helper 做目标校验与 DOM 写读；阶段模块在显式调用时组合暂存、质检或上传并自动保存回执，不点击最终提交。专业判断与本地三模型门槛继续沿用既有流程。
- 实测确认：点击可能先触发请求再抛超时；换行规范化会使旧配方误报；当前三项结果标签不同；修改输入清空检查结论，恢复文字不恢复回执。具体防重发与恢复步骤集中在平台操作流程。
- 公共代码仅含通用逻辑，回归使用合成 DOM；私人实测材料保留在忽略目录。此次不重新发起线上质检或模型生成。ego 长截图已按 §12 复用已有会话重验，仍采用整视口拼接及目视完整性核验。
- 验证：新增 Node 合成测试 8 项全过，并由 Python unittest 包装纳入发现。原生 Windows 设置 `PYTHONUTF8=1` 后，全量为 288 项；与修改前 287 项对照，均有 8 个失败、165 个错误，失败用例集合相同，无新增失败。现有阻碍包括缺少 `markdown_it`、POSIX 权限检查及 Windows 路径/符号链接行为，不能声称全量通过。文档相对链接与 `git diff --check` 通过。


状态：已实施（2026-10-24）。依据 2026-10-24 用户指示调整：**自动化分支只提供流程与规则的指导，不新增强制的阶段检查与门禁**。配套文档：[需求讨论稿](AUTOMATION_DISCUSSION.md)（已确认决策与轻量化调整）、[自动化操作手册](../skills/llm-authoring-workflow/references/automation-playbook.md)（已验证浏览器操作，位于 Skill references 目录，供流程指导各阶段绑定必读）。实施结果：阶段 A–D 与 F 全部完成，新增 7 项合成测试全部通过，全量对照零新增失败；剩余失败均为仓库既有的原生 Windows 环境问题（正式验证环境为 WSL/Linux）。

## 1. 目标与轻量化原则

在现有流程开头增加可选自动化分支：用户指定大方向后，助手自主完成选题、设计、检查、pi-web 采集、三模型评估、平台网页质检与截图上传，到 Arena 入口暂停交回手动。

实现原则：

- **指导而非强制**：阶段顺序、计数规则（预算、方向切换、重取、修复轮）、暂停条件全部写入流程指导文档，由助手自觉执行并记录；不新增专业质量门槛；配方的目标、输入绑定及防重放校验保护既有操作。
- **复用现有命令**：设计、冻结、模型输入、评估、Arena 准备均用现有 lab 命令，不新增命令族。
- **浏览器操作不入库**：pi-web 与平台操作由助手按[自动化操作手册](../skills/llm-authoring-workflow/references/automation-playbook.md)执行，验证过的操作经验全部沉淀在该手册中。
- **本地三模型门槛保留**：`lab check` 的 three_model_gate（Seed 未全达成且 GPT/Claude 至少一个全达成）是现有核心质量标准，自动化分支照常经过，不算新增门禁。

## 2. 任务配置：关闭本地平台检查门禁（唯一功能性代码改动）

现有代码已内置开关：`TASK.json` 的 `platform_checks_required` 为 false 时，`question_gate`/`final_gate`/`stage_gate` 全部直通，`choose-model-checks` 进入 legacy 已配置状态，`export_evidence` 跳过——本地不做任何平台检查强制。

改动：`lab new <题目编号> --no-platform-checks`（`workspace.py` 任务创建 + `cli.py` 注册参数），自动化任务用此开关创建，`platform_checks_required` 置 false；手动任务默认不变（True）。此外 `lab status` 对该类任务不再提示平台检查阶段。

三项质检仍照常**在平台网页上真实执行**（Q8 既定决策）：约束来自平台自身的"确认后继续"机制与流程指导，不再由本地工具强制；结果按第 4 节约定记录。

## 3. 流程指导文档（主要交付物）

新文件 `skills/llm-authoring-workflow/references/automation.md`，内容骨架。**每个涉及浏览器操作的阶段必须绑定[自动化操作手册](../skills/llm-authoring-workflow/references/automation-playbook.md)的对应章节为必读**（阶段开头注明"先读手册 §N"），使已验证的操作经验（定位方式、事件序列、完成判据、陷阱规避）成为流程的组成部分，而不是可选参考：

0. **入口**：开始时询问手动/自动化；自动化任务用 `--no-platform-checks` 创建；记录大方向（同一会话沿用，上下文丢失时从最近任务 WORKLOG 恢复）。
1. **候选设计**：按 design.md/writing.md/研究报告选题与写作（题面单问、≤100 汉字、Insight/考点标准）；用 `memory-context` 读全库索引做实质避重与方向覆盖（软偏好）；填平台表单并运行难度标签辅助判断（通过线为难度系数 ≥6，过简单即重新设计，返修不设硬性轮数上限）；平台通过后本地完成考点、设计复核并冻结（现有命令）。
2. **Seed 采集与本地判断**：`model-prepare seed` → 按手册 pi-web 独立会话采集（型号/high/仅聊天三项核对）→ 填写文件 → `model-import seed` → seed 评估与 `seed-check`。**只做本地判断，不向平台填写任何模型信息。**Seed 全部达成则记失败候选、换新候选。
3. **GPT/Claude 采集与三模型本地确认**：Seed 未全达成时 `model-prepare gpt/claude` → 两个独立会话采集导入 → 三模型统一评估 → `lab check` 确认 three_model_gate。初次两家均未达成时保留有效原文及负结果并淘汰候选；后期修复需要替换有效回复时按本次明确授权处理。确认的技术失败与内容未达成分开，未知请求不重发。**本地门槛确认前不填平台模型区块**：被淘汰的候选不产生平台填写与草稿替换。
4. **平台模型信息填写与质检**：三模型门槛本地确认后，**一次性填写**平台三个模型区块——各模型回复原文、本地达成判断结果、逐考点备注（豆包选"未达成"后 GPT/Claude 区块自动出现，按手册键盘法选择）；填写完成后运行考点质检与达成性判断。认可的不通过按专业依据修订并统一重评后平台重跑（修复轮自律上限 2 轮）；有依据的异议填平台备注后继续；调用异常按平台规则选"异常"并备注。
   填写时机总原则：**平台提交信息只在本地可确认的内容确认之后填写，每项检查在其所需输入完备后运行**——题目阶段信息（类型/领域/Prompt/Insight）在阶段 1 设计确认后填写并过难度检查；模型阶段信息（三份回复、达成判断、备注）在阶段 4 三模型门槛确认后一次性填写，再运行后两项检查。
5. **截图**：三会话 pi-web 截图（问题/回答/型号/档位截全，滚动分段）→ 归档任务目录 → 平台上传。
6. **Arena 交接**：`arena-prepare`（本地仅需 three_model_gate）→ 向用户发 Arena 填写入口，自动化结束。
7. **暂停与恢复**：登录失效、验证码、型号无法确认、发送结果未知时暂停并记录断点，恢复按手册协议；失败计数只计被淘汰的不同候选（返修、修复轮、重取不重复计），同一细分方向连续 5 个候选失败换方向，候选总数自律上限 10（可调），达到即停止并汇总失败分布。

## 4. 记录约定（WORKLOG.md，agent 自律维护）

automation.md 规定在任务 `WORKLOG.md` 用固定小节记录，作为恢复与对账依据（重启不重置，因为没有重置机制）：

- 候选登记/失败与原因、方向连败计数、重取与修复轮计数；
- 采集阶段结果及证据目录；会话、界面型号、high、结束状态和哈希由采集回执自动保存；
- 平台检查结论、关键设计决定及异议/异常；输入、调用前后状态、完整结果由阶段模块保存；
- 截图归档路径与上传完成标记。

来源说明：pi-web 回复经标准填写文件与 `model-import` 入库，元数据为现有 manual 语义；pi-web 会话级溯源（型号/级别/会话）记录在采集回执，WORKLOG 引用其目录，保证任务记录诚实可查。如以后需要把来源写入结构化元数据，作为可选增强另议。

## 9. 性能优化轮（2026-10-25，已实施）

用户首跑反馈单题浏览器操作过慢、额度消耗高。决议（grill 确认）：混合路线——平台用页面配方脚本、pi-web 用本地 HTTP API、平台不复刻 HTTP 接口、不设速度硬指标。

- **配方库**（`skills/llm-authoring-workflow/references/automation-recipes/`，七项全部真实环境端到端实测通过）：题目表单填写、模型区块填写、截图上传（100KB 实测）、质检运行、三态读取（结构性消除"重跑瞬间残留文案被误判为调用异常"）、Agent 正常/异常标记+异议备注、pi-web HTTP 采集（ap/gpt 双通道实测）。关键机制：antd 下拉 React fiber 直调 onChange（内置全部 label→value 映射）、文本域原生 setter、截图上传 DOM 属性中转+主世界注入、evaluate 表达式求值（DATA 在 IIFE 内）。
- **接线**：操作手册开头"配方优先"原则、§1 采集主路径改为 HTTP、§2 各步骤指向对应配方（手册原步骤保留为回退与 needs_manual 补齐路径）、§5 配方库清单与使用规则；automation.md 第 6/8/9/12/13/14 步改为配方主路径。
- 回退契约：配方返回 `needs_manual`/`not_present` 或整体失败时，按手册对应小节逐项操作，不算异常、不谎报成功。
- 预期效果：每题平台侧浏览器操作从 40+ 次降到约 4–6 次配方调用加少量补齐；pi-web 采集零浏览器操作（截图除外）。

## 10. 长截图轮（2026-10-24，已实施）

用户要求长回答合成**单张长图**而非分段多图。验证结论：截图接口的 `clip` 截取会产生横向平铺伪影（合法坐标 984 宽截取，输出第 640 列起逐列重复开头 344 列，拼出的图呈"一图两页"假象；fullPage 伪影同族）——**clip 与 fullPage 一并禁用，一律整视口截图**。最终方案：滚动分段整视口截图 → `stitch-screenshots.py`（新配方，本地 Pillow）逐列查重校验 → 容器矩形裁边 → 内容坐标衔接（段间重叠按次序裁掉，高度守恒校验）→ 末段附底部栏条带 → 单张长图。正用例与手工拼接逐像素一致、负用例（伪影图）被正确拦截；几何必须在截图时刻实时测量，不用早前旧值。曾评估"临时调高视口一次成型"方案（视口上限 3840×2160），用户选择维持多段拼接路线后放弃。手册 §1.10、§3 陷阱清单、§5 配方库（八项）与 automation.md 第 14 步已同步更新。

## 11. 试用反馈轮（2026-10-25，已实施）

首次真实自动化试用（一题成功交付、一题连败暂停）暴露三个问题，经 grill 讨论定稿。核心决策：自动化任务内解锁换向；难度改善只做设计侧约束增强（不切会话模型，避免人工介入）；知识库由助手自写、广泛搜集、覆盖全部商科细分方向。探查事实见本轮讨论记录：方向锁= `CURRENT.json` 存在后三把锁（领域/子方向/题型）仅允许新建题目绕过（selection.py:50、workspace.py:186/171），无 force 途径；试用任务实证连败 5 次后任务锁死（WORKLOG 记"结构性不可执行，等待用户决策"）。

### 11.1 自动化任务换向解锁（唯一代码改动）

背景矛盾：自动化分支既定决策"一次运行=一个任务、候选=任务内 rNNNN 冻结版本"（讨论稿"已确认范围"节），与方向锁组合导致"连败 5 换细分方向"（automation.md 第 16 步）只能新建任务、预算计数割裂。

- `llm_authoring/selection.py` choose_subdirection：冻结后的换向拦截仅对手动任务（`platform_checks_required=true`）生效；自动化任务允许更换分支并正常写入 REQUEST 字段（business 子方向为平级叶节点，自动确认语义不变）。
- `llm_authoring/workspace.py` choose_type：同样按任务类型放行（自动化任务冻结后可换题型；WORKLOG 格式示例本就假设题型可变）。
- `llm_authoring/workspace.py` choose_domain：**不变**——大方向两分支均保持"仅用户明确要求可换"。
- freeze 的 validate_selection 不变：候选 subdirection/题型必须等于 REQUEST 当前记录，保证换向后新候选与新方向一致；旧冻结候选与 CURRENT 指向不受影响。

测试：自动化任务冻结分支 A 候选后换子方向/题型成功、后续冻结落在新方向（rNNNN 顺延、旧候选不动）、换大方向仍被拒；手动任务冻结后换子方向/题型仍被拒（selection.py:50 现无测试覆盖，补齐）；既有 domain 锁测试不回归。

流程文档：automation.md 第 2 步注明自动化任务冻结后可直接 `choose-subdirection`/`choose-type` 换向并记 WORKLOG；第 16 步换向规则改为可执行，换向后连败计数按新细分方向重新起算。templates/AGENTS.md 不变（手动分支语义不变）。

连败暂停任务的恢复：实施后原地续跑——换到零覆盖细分方向（现状 analytics=2、accounting=8、其余 5 个方向 0 条），连败重新起算；恢复时先修正 WORKLOG 顶部滞后字段（如"已淘汰候选：0"旧值）。

### 11.2 难度与区分度设计规则 + 送检自检（文档改动，两分支共用）

背景（试用实证）：难度迭代消耗 17 次平台调用（v1=2 过简单"推理机械"、v2=5"关键收支顺序缺失无法唯一推出"、组合=2、EVPI=4、口径=2）；幸存候选主死因为 Seed 全达成（5 个失败候选中 4 个 seed_fully_attained，均为信息完备的封闭计算题）。对照任务一次通过难度 8 且五模型区分度良好：决定性考点在口径定义/方法论/推断有效性层。教训已在 failure_observations 但未沉淀为设计规则。

- `design.md` 新增"难度与区分度定位"节（两分支共用）：
  - 术语区分：难度系数（平台对题面的打分）≠ 区分度（决定性考点在不同模型间产生达成差异的能力）。
  - 规则一（区分度定位）：决定性考点须落在口径定义、方法论选择、推断有效性或多约束交互层；信息完备、全部决定性考点可由题面数字封闭计算得出的题设不得作为候选主轴（附 1061/1168 实证说明）。
  - 规则二（唯一可解）：题面须唯一确定结论——关键信息缺失导致无法唯一推出会被平台打回；目标是"唯一可解，但解路径需要方法论判断"。
  - 规则三（防挖坑边界）：区分度必须来自任务本质的方法论判断，不得为压分给 Seed 挖坑（呼应 authoring.md"不用冷僻陷阱考倒模型"）；规则与自检不替代平台检查。
- `automation.md`：
  - 第 5 步加送检自检（两条问句，助手执行约 1 分钟，WORKLOG 记一行结论）：① Seed 推演——逐决定性考点问"是否只靠题面数字标准计算即可答对"，存在即先改题设不送平台；② 唯一可解——题面是否唯一确定结论。
  - 历史记录修正现由 §13 覆盖：每次结果由阶段模块归档，WORKLOG 只记决定与证据位置。
  - 历史效果指标留作维护研究基线（难度调用次数/候选≈4.3、Seed 全达成占比 80%）；日常做题不统计填表或自行撤销规则。维护复盘从既有记录汇总，专业自检保留。
- 词汇表：CONTEXT.md 已补"难度系数""区分度"（连同上轮"题库""知识库"）。
