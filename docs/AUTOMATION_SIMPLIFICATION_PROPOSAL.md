# 自动化分支流程精简与可靠性优化审阅稿

状态：用户已授权按推荐方案实施（2026-10-26）。实现与验收见 [AUTOMATION_SPEC.md §13](AUTOMATION_SPEC.md#13-流程精简与恢复优化2026-10-26)；本文保留问题分析及方案依据。

后续规则调整：自动化后两项先处理考点，再由agent按结果、有效异议或平台允许的异常跳过判断是否运行达成性，不设程序性结论门槛；并允许每题面/Insight/考点内容版本GPT/Claude各补取一次。见[AUTOMATION_SPEC.md §14](AUTOMATION_SPEC.md#14-顺序质检与版本补取2026-10-26覆盖此前冲突条款)。本文原“不自动补取”和“两项并行”仅保留历史讨论，不作为现行指令。

本方案覆盖自动化分支从启动到 Arena 交接的操作流程，目标是轻量、快速、准确。建议保留当前技术路线：pi-web 原生 HTTP 采集、ego 批量文本与标准控件操作、真实会话分段截图、现有 lab 导入及专业判断。

本轮优化重点是减少重复登记、临时脚本编排和无效等待，将已验证的动作组合成少量可复用操作。本文保留提案结构；日常执行使用已更新的 automation.md 和站点配方，避免把审阅讨论当作额外操作步骤。

## 1. 总体判断与优化边界

当前主线顺序基本合理：确认环境 → 设计与题目检查 → 冻结 → Seed → GPT/Claude → 三模型判断 → 平台填写及后两项检查 → 截图上传 → Arena 交接。Seed 优先及门槛前不填平台模型区块，能够减少失败候选的无效操作。

主要负担集中在阶段衔接。已有模块解决了单次操作，但助手仍要临时组织调用、解释状态、保存记录、复制原文及确认下一步。相同证据又出现在模块文件和 WORKLOG 中，增加维护成本。

| 要求 | 本方案的具体含义 | 不采用的做法 |
|---|---|---|
| 轻量 | 事实自动记录一次，助手只记录重要决定；沿用现有文件和模块 | 新建调度服务、任务数据库、审批链或重复专业门禁 |
| 快速 | 复用阶段函数、合并浏览器往返、利用服务等待时间 | 为速度跳过保存确认、重复发送结果未知的请求 |
| 准确 | 用目标、输入、会话和本次结果建立关联；异常返回可执行原因 | 把点击成功当检查通过，把可见旧结果当本次回执 |

轻量的衡量对象是操作量和维护成本。少量自动生成的防错记录应保留，不以减少文件数量为目标。

## 2. 问题清单与解决方案

### 2.1 同一信息重复登记

**现状。** pi-web 已保存意图、回执、API 快照和结果清单；自动化流程还要求 WORKLOG 登记型号、high、会话/回复 entry ID、题面哈希及结束状态。平台质检也要求完整输入和回执落盘，再逐次写入 WORKLOG。

**影响。** 助手花时间抄写可计算的信息；一处更新、另一处遗漏时，恢复流程反而难以判断哪个记录可信。

**建议。** 明确记录分工：

| 信息 | 唯一维护位置 | WORKLOG 如何使用 |
|---|---|---|
| 冻结题面、版本、评估及已导入回复 | 现有 lab 文件 | 引用版本或评估路径 |
| 发送意图、会话、哈希、回复来源及结束状态 | pi-web 模块已有记录 | 写结果摘要及目录链接 |
| 本次平台检查输入、触发证据、完整结果 | 平台阶段函数自动保存的检查记录 | 写结论、重要异议及证据链接 |
| 截图几何、原段、成图与上传关联 | 截图及平台操作记录 | 写完成状态及路径 |
| 用户决定、换向理由、需处理异常、当前断点 | WORKLOG | 简短直接记录 |

普通状态轮询不逐条写日志；仅记录开始、重要状态变化、完成及异常。各次难度系数与理由保留在检查回执中，需要复盘时自动汇总，不再要求人工重复摘录。

建议的 WORKLOG 摘要：

```text
当前：r0002，三模型门槛通过，等待平台后两项检查。
连接：沿用本任务已确认的服务地址、答题目录和平台目标。
采集：三个角色完成；证据见对应版本的采集目录。
决定：上一候选 Seed 全达成，已保留原件并换题。
下一步：读取本次检查结果；截图已在本地准备。
```

**验收。** 同题恢复可从简短 WORKLOG 找到当前阶段及原件；无需手动重录哈希或会话字段；记录不一致时以原件及当前实际状态核对，不凭摘要直接重放。

### 2.2 已验证动作仍依赖临时编排

**现状。** 平台模块目前提供 `fillTextBatch`、`readTextFields`、`scrollToField`、`readChecks` 等基础能力。保存确认、调用前后状态关联、轮询归档、上传完成核验仍由每轮执行脚本组织。pi-web 归档后写入准备文件也尚需助手接线。

**建议。** 在现有模块上补充少量阶段操作；以下名称表达职责，实施时可按已有结构调整，不新增公共 CLI 命令族。

| 阶段操作 | 组合的已有能力 | 返回什么 |
|---|---|---|
| 角色采集与接续 | 读固定尝试目录 → 首次发送或只读观察 → 成功归档 | 运行中、完成、需处理问题及证据路径 |
| 原文写入与导入 | 读取归档 → 核对 lab 当前版本/准备文件 → 按字节写入 → 现有 model-import | 导入结果或具体冲突 |
| 平台阶段填写 | 批量文本、标准选项控件 → 统一回读 → 保存确认 | 已保存或差异字段 |
| 平台检查 | 保存调用前输入/状态 → 单次点击 → 观察 → 归档 | 各项当前状态及回执路径 |
| 截图准备与上传 | 连续采集 → 拼接 → 目视检查 → 标准上传及保存核验 | 本地图、上传状态及失败位置 |

阶段函数只执行已经确定的动作，不判断专业考点，不代替 `lab check`，不自动批准重取。等待仍按短窗口续接，不建立常驻调度器。

新增操作必须处理“前半段成功、后半段失败”。再次调用时先读取既有证据：已发送就只观察，已归档就复用，已导入就核验相同原文，已上传就查看对应预览。不能因为后续步骤失败而重跑整段。

原文写入只允许目标是工具生成的占位文件或同一份原文；遇到不同有效回复，转入既定替换规则。暂时无法识别的平台状态返回具体原因，由助手处理，不通过猜测继续写入。

**验收。** 在已验证页面和版本下，一次阶段调用可完成其确定性操作；正常路径不需要重新编写控件定位、状态解析或归档逻辑。可恢复失败不重复触发生成、质检或上传。

### 2.3 分支规则与重取权限存在歧义

**现状。** README 的手动流程口径包含“不调用模型 API、不生成截图”，但自动化段又使用 pi-web 与截图。自动化第 9 步允许未达成角色补取一次，而 AGENTS 中存在初次门槛失败换题及替换原回复须明确同意的规则。自动化网页后两项固定检查，与通用可选质检说明也需明确适用范围。

**建议。** 入口先确定分支，再加载该分支执行规则；共同专业标准继续共用。正文注明“手动分支”或“自动化分支”，不依靠助手自行推断例外。每种规则只保留一个执行说明，其余位置用短链接指向。

重取与后两项质检涉及用户选择，具体方案见第 5 节。本文不将技术封装当作授权扩大，也不把审阅文档视为同意替换回复。

**验收。** 对同一个失败场景，AGENTS、SKILL、主流程和配方给出一致下一步；正常任务不因文档矛盾重复询问或自行增加检查。

### 2.4 错误分类过粗，可能持续无效等待

**现状。** `piweb-client.mjs` 的 `watchAttempt` 将观察过程中所有异常统一归为 `read_error`。这些异常可能来自网络，也可能来自题面哈希变化、私有记录损坏、配置错配或接口结构变化。文档对 read_error 的一般处理是继续读取。

**建议。** 保留有限、明确的错误类别，并给出具体下一步：

| 情况 | 处理 |
|---|---|
| 暂时网络错误或可恢复读取失败 | 保留会话，短窗口内适度退避，只重试读取 |
| 服务不可达持续出现 | 报告连接故障并保留断点；不将模型判失败、不无限密集轮询 |
| 认证失效 | 提示处理当前服务登录或私有认证配置 |
| 题面变化、记录损坏、版本或配置错配 | 立即返回具体冲突；停止该角色的导入/发送，先核对原件 |
| 接口结构不兼容 | 返回诊断；采用已核实的读取回退或维护适配器 |
| POST 结果未知 | 从原会话只读核对；无法确认则保存断点，不重发 |
| 正常生成或服务内部重试 | 持续等原请求，无生成总时限 |

网络等待与正常生成分开处理。观察窗口结束不代表生成超时，也不授权新请求。错误输出保留可诊断的字段与阶段，不输出认证头、密码或全文敏感载荷。

**验收。** 网络暂时失败后可恢复；题面被改、401、记录损坏不会反复显示“仍在等待”；任何恢复路径不增加第二次 POST。

### 2.5 独立工作没有利用等待时间

**现状。** 主流程通常在后两项检查结束后才开始制作三个会话截图。

**建议。** 三模型门槛通过后，平台填写并确认保存，发起本题要求的后两项检查；保持平台页和检查输入不动，在同一授权空间的独立 pi-web 页面制作截图与拼接。每完成一张图或一个短观察窗口，回读平台状态并报告有意义的变化。

检查结束、版本及会话关联仍有效后再上传。若仅修 Insight/考点且回复未更换，已核验的会话截图可复用；若改题或替换回复，则只重做受影响角色的截图。已有成图的复用依据是会话、回复 entry ID、正文关联及可见型号/high，而非文件名相同。

GPT/Claude 在符合采集条件后也可并行发起；各自保持独立会话、意图与结果。浏览器对同一个页面的写操作仍顺序执行，避免两个脚本争夺滚动或输入状态。

**验收。** 等待期间没有修改平台依赖输入、刷新或关闭平台页；截图与当前回复一致。总耗时按“模型生成、平台等待、实际操作”分开比较，不把模型速度计作浏览器优化收益。

### 2.6 重复校验和回读可以合并

**现状。** 平台每个 DOM helper 已校验目标 itemID，但示例仍单独调用 `verifyTarget`；批量填写会返回即时匹配结果，随后还要另读文本、控件、保存及阶段状态。部分重复是为确认 React 更新和服务端保存，但可以在同一阶段函数内完成。

**建议。** 保留每次写操作内部的廉价目标校验，省去调用方无意义的独立往返。统一采用“批量写入及控件操作 → 等状态稳定 → 一次读完整阶段字段 → 确认保存”。不能只用即时 `domMatches` 取代异步更新后的回读。

全页 snapshot 用于首次接入、页面结构变化或异常定位；正常路径读取所需的小 JSON。刷新仅用于首次适配、恢复后存在持久化疑虑或交接核验所需的场景；同一阶段满足条件时合并为一次刷新，不每字段刷新。保存动作仅在实际有修改时执行。

模型目录在同一运行中预检并复用；配置变化或请求异常后刷新。保持配置关联核验，不要求上游实际模型 ID 与界面名称相同。

**验收。** 正常填写一次统一回读能覆盖文本、下拉、保存状态；字段差异只补相关字段；未改字段不会重复触发 change 导致质检失效。

### 2.7 维护统计混入日常主流程

**现状。** 自动化第 6 步要求跟踪难度调用次数和 Seed 全达成比例，并在五个候选后判断是否撤销自检、回写规格。“无明显改善”缺少明确比较条件，也要求日常出题任务修改全局规则。

**建议。** 保留已有专业自查、研究报告和设计复核；取消同一结论在 WORKLOG 的重复抄写。同一上下文已经完整阅读的资料按检查单应用，不反复全文读取；上下文丢失、资料变化时补读。

效果统计从既有记录按需汇总，放到单独的维护复盘。正常出题任务不根据少量样本自动撤销标准或修改仓库规格。候选预算、方向连败、返修上限继续沿用，计数优先从既有事件推导，助手只记录例外理由；本轮不新增成功率或耗时硬门槛。

**验收。** 做题路径不再包含效果研究和全局规则回写；仍有专业依据、必要自查及可恢复的预算/候选计数。

## 3. 建议的正常执行路径

1. **一次启动。** 一次收集尚缺的分支、大方向、服务地址、答题目录及平台目标。用户已明确的信息直接沿用；同题恢复从 status、WORKLOG 和既有证据续接。新任务仍按用户要求确认实际 pi-web 地址，不设默认值。
2. **设计与题目检查。** 查题库和资料，完成自然题面、Insight 与专业自查；平台阶段函数填写、确认保存并运行题目检查，自动保存每次结果。依据反馈修订，完成考点和设计复核后冻结。
3. **Seed 采集。** 调用采集接续操作，按冻结题面发送一次、等待并归档；安全写入及现有 lab 导入，然后由助手完成专业判断。
4. **后续两模型。** Seed 未全部达成且适用规则允许时，GPT/Claude 独立并行采集。完成同版判断及 `lab check`；失败按审定的策略处理。
5. **平台填写与检查。** 门槛通过后批量填考点、原文、判断和备注，一次统一回读并保存。按本题合同发起后两项检查，两个检查可并行。
6. **利用等待制作截图。** 平台请求等待期间，独立页面逐会话截图、拼接和目视核验；平台输入保持不变。
7. **上传与交接。** 当前结果和证据关联明确后上传，核验对应区块预览与保存。执行现有 Arena 准备，交付链接及真实检查状态，由用户继续既定手动环节。

专业研究、语义去重、考点判断、反馈是否合理以及最终图目视核验仍由助手完成。机械操作尽量由函数执行；正常路径没有额外审批点。

## 4. 保留的必要保护

| 保护 | 实现位置 | 保留原因 |
|---|---|---|
| 目标题号/itemID、版本及会话关联 | 写入函数内部与阶段入口 | 防止写错题、采错回复 |
| 冻结题面精确发送、原文按字节保留 | 采集/导入模块及既有 lab 校验 | 防止模型输入不一致或原回复被改写 |
| 界面显示型号、high、仅聊天 | 模型目录关联与页面核验 | 满足用户指定的模型采集条件 |
| 发送前记录与未知请求不重发 | 现有私有意图/回执 | 防止断线造成重复调用 |
| Seed 顺序及三模型门槛 | 现有 lab 与专业判断 | 保持题目筛选要求 |
| 当前输入对应的实际质检结果 | 平台检查阶段函数 | 防止误收旧结果或把服务异常算通过 |
| 保存完成、上传完成与最终图核验 | 平台/截图阶段操作 | 防止仅本地显示成功或截图缺段 |
| 回复替换、Arena 与最终提交边界 | 审定规则及用户授权 | 保持原件和人工交接要求 |

这些保护优先复用现有实现，不另建一层重复检查清单。

## 5. 需要审阅的规则选择

本次已按推荐列落实以下四项选择，不作为以后每一步的新增询问。

| 议题 | 推荐方案 | 其他方案及影响 |
|---|---|---|
| 有效回复未达成后的补取 | 区分技术失败与内容未达成：已有有效原文不自动替换；初次双模型未达成按高层规则换候选，专业返修后仍需换回复时按明确授权处理。统一删除或修正与之冲突的自动补取条款 | 若希望自动化固定允许补取一次，需明确批准角色、次数、适用阶段及原件归档，再统一写入分支规则；不能靠现有歧义推定授权 |
| 自动化后两项检查 | 将当前自动化分支说明中的“三项网页检查”明确为该分支合同；通用可选 API 检查说明限定手动适用，既有明确用户选择优先保留 | 若自动化也允许跳过，应明确选择时点和交接口径，沿用已有选择能力，不新建一套策略记录；需另核对平台交付要求 |
| 日常效果统计 | 移出做题主流程，维护时从已有记录汇总；保留专业自查 | 保留统计也应自动生成，不再要求助手逐题抄写或自行修改全局标准 |
| 两段式发送 | 当前单次 POST 继续默认；两段式作为恢复能力候选，待正常任务验证真实发送后再评估切换 | 立即切换会把未完成的真实发送验证引入主路径；本方案不建议 |

用户已确定的“界面显示型号正确即可”和“自动化启动时确认实际地址”直接保留，不列为待选事项。

## 6. 实施顺序与文件范围

| 阶段 | 具体工作 | 主要落点 | 完成依据 |
|---|---|---|---|
| A 规则与说明精简 | 按审阅结果统一分支、重取、质检说明；缩减 WORKLOG；移出日常效果复盘 | README、AGENTS、SKILL、automation.md、相关质检/返修引用 | 同一场景下一步一致，无新增审批或重复登记 |
| B 错误与恢复修正 | 区分读取故障和本地完整性错误；明确只读恢复；补中断用例 | piweb-client.mjs、piweb-http.md、合成测试 | 致命问题立即可诊断，暂时故障可恢复，零隐式重发 |
| C 阶段操作封装 | 采集接续、归档写入、平台填写/保存、质检关联和上传核验 | 现有 automation-recipes 模块；确有需要时拆一个小型辅助模块 | 常见路径直接复用，不再临时拼定位/等待/归档逻辑 |
| D 等待时间并行与回读合并 | 后两项并行、等待中截图、统一阶段回读及按需刷新 | automation.md、automation-playbook.md、平台/采集说明 | 同页操作不争用，版本一致，独立工作有效重叠 |
| E 验证与发布准备 | 合成回归、已有会话/可逆页面验证、检查公共内容 | tests、规格及私有验证记录 | 新增用例通过，既有回归可解释，验证范围表述准确 |

实现优先放入已有模块。只有职责明显不同或文件难维护时才新增文件；不引入常驻服务、外部队列、工作流数据库或统一状态机框架。现有任务从真实断点续接，不为新目录结构迁移或重取历史回复。

## 7. 验收方法

### 7.1 轻量与速度

选取同类任务，记录实际阶段调用次数、全页快照次数、人工维护条目和正常路径临时脚本量。记录从执行过程自动产生，不能为了测效率增加每步填表。

预期可检查的变化是：正常路径不再抄写机器字段；每个填写阶段一次统一回读；独立检查与截图存在时间重叠；恢复不重做已完成阶段。减少多少时间以实际样本为准，不预设固定倍数或秒数。

### 7.2 准确与恢复

使用合成数据和模拟服务验证：

- 发出请求但回执丢失，恢复只读且没有第二次 POST。
- 题面被修改、记录损坏、认证失效时返回不同原因，不持续伪装为生成等待。
- 归档完成但尚未导入、导入完成但摘要未写、上传派发成功但调用返回异常时，从实际断点续接。
- 平台旧结果仍显示、输入改变导致结果失效、点击报错但服务已开始时，不误判完成或重复触发。
- 错题号、错误角色区块、已有不同原文、缺失/重复控件时停止相关写入，指出具体冲突。
- 检查等待期间平台输入不变；会话未变时截图复用，回复替换后旧截图不误用。

真实验证优先复用已有会话、只读观察及获准的可逆操作；真实生成与真实质检只在适用授权内执行。当前验证基础为 13 项 Node 与 5 项 Pillow 新增测试通过，以及短/长/代码表格会话截图实测；两段式仅空会话创建已实测。

此前同一 Windows 环境全量回归为 294 项、8 failures / 165 errors，与修改前失败项目一致；其中包含缺少 markdown-it 和平台兼容问题。它只能支持“未新增已知回归”，不能替代完整通过。发布准备应使用依赖齐全、符合仓库要求的测试环境；仍有失败时逐项说明，不将环境修复变成日常做题门槛。

## 8. 审阅结论入口

第 5 节推荐选择已获本次实施授权，已按 A → B → C → D → E 实施并验证。技术优先级最高的是记录去重、错误分类和阶段操作复用；并行优化随后接入，避免将尚未稳定的恢复逻辑并行放大。

本方案实施后的目标是：助手把精力放在出题、判断和异常决策上，已验证的机械步骤由程序重复执行，用户只在既定选择或确有阻碍时介入。
